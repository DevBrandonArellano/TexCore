Enfoques de Arquitectura — Microservicios Independientes

¿Cómo estructura Django la API interna que consumen los microservicios?

A

Internal API Layer dedicado

Se crea un namespace /api/internal/v1/ exclusivo para comunicación servicio-a-servicio. Endpoints diseñados para las necesidades exactas de cada microservicio.

✅ Pros

  • Separación clara: API pública vs interna
  • Versionable independientemente
  • Auditoría perfecta (ISO 27001)
  • Endpoints exactos para cada caso de uso

⚠️ Contras

  • ~20 endpoints nuevos en Django
  • Más código inicial

⭐ Recomendado — alineado con ISO 27001 + COBIT

B

Reusar endpoints DRF existentes

Los microservicios consumen los mismos endpoints que usa el frontend React, autenticados con JWT de servicio en lugar de JWT de usuario.

✅ Pros

  • Cero endpoints nuevos en Django
  • Reutiliza lógica ya testeada
  • Implementación más rápida

⚠️ Contras

  • Mezcla tráfico de usuarios y servicios
  • Endpoints devuelven datos extra que el servicio no necesita
  • Difícil versionar sin afectar el frontend
  • Audit trail menos granular
C

Django Service Layer expuesto como API

Los microservicios no llaman endpoints REST — Django expone sus servicios internos (gestion/services/) via un bus de eventos interno con Redis (Celery ya instalado).

✅ Pros

  • Desacoplamiento total (asíncrono)
  • Alta resiliencia
  • Escalable a producción real

⚠️ Contras

  • Complejidad alta para tesis
  • Scanning necesita respuesta síncrona
  • Requiere diseñar esquema de eventos
  • Overengineering para el alcance actual

Contexto de decisión

Con JWT Service Tokens (tu elección) + Internal API Layer, cada microservicio tiene una identidad única en Django. Django puede registrar en el audit log: "scanning_service consultó lote #4521 a las 14:32" — esto es exactamente lo que exige ISO 27001 A.12.4 (registro de eventos).
